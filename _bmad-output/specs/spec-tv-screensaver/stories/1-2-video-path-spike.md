## Intent

**Problem:** Every video decision (player, HDR, frame rate, loop) rests on unverified assumptions about the X90K: the Flutter UI plane is 1080p, the TV exposes only one display mode (3840×2160 @ 60 Hz), and nobody has checked texture vs SurfaceView sharpness, HDR pass-through or a gap-free looping clip with sound.

**Approach:** Extend the TV Saver app with a remote-driven video test screen that plays adb-pushed clips in texture and platform-view (SurfaceView) mode, logs what the TV/player report, and ship `tool/video/` scripts that generate the 4K test clips. Kay judges sharpness, HDR badge, judder and loop gap on the TV; findings go to the spec memlog. Dolby Vision is out of this story.

## Boundaries & Constraints

**Always:**
- Nothing ever changes a setting on the TV: adb is read-only apart from `adb install` and `adb push` into the app's own external files dir (`/sdcard/Android/data/com.codedbykay.tvsaver.tv/files/spike/`). The 24p test may rely on Kay switching "Match content frame rate" by hand.
- Prefer `video_player` with `VideoViewType.platformView`; if it cannot expose what the checks need (frame-rate strategy, gap-free loop), embed a Media3 `PlayerView` as a platform view in this story. Auth headers and the Pi are not part of this story (local files only).
- Clips are generated by `tool/video/*.sh` with ffmpeg (install via `winget install Gyan.FFmpeg` if missing; PC only). Clips live in git-ignored `build/spike-media/`; total pushed to the TV ≤ 1.5 GB; check free space read-only first.
- Test clips (each ≤ 20 s): (1) 3840×2160 HEVC Main10 SDR with 1 px black/white line pairs and a gradient; (2) the same pattern as HDR10 (PQ/BT.2020 metadata); (3) HLG; (4) 23.976 fps horizontal pan for judder; (5) a ≤ 10 s clip with AAC stereo "crackle" audio (noise bursts) and a visible frame counter, for loop-gap testing.
- The spike screen is operable with the TV remote only (D-pad list of clips, keys to toggle texture/platform view and loop mode).
- The app logs a `VideoSpike:` line per run (clip, mode, decoder name, HDR type, active display mode/refresh rate, dropped frames) and the MediaCodecList decoders (HEVC profiles, AC-3/E-AC-3) at startup.

**Never:**
- No Pi, networking, library, playlist, pairing or hub code. No Dolby Vision clip or tooling (deferred, logged in the memlog).
- No TV settings changes; no system-wide display tweaks.
- No production polish: this is a spike. Kept: the `tool/video/` generators and the findings.

## Implementation Notes

- Player: `video_player` for the texture and platform-view rows; a native Media3 `SurfaceView` platform view (`tvsaver/media3view`, channel `tvsaver/video`, `VideoSpike.kt`) for the media3-surface row and the two-item playlist loop, because `video_player` cannot loop gap-free or report decoder/dropped frames. Media3 default frame-rate strategy; 24p depends on the TV's "Match content frame rate" being switched by Kay.
- ffmpeg installed on the PC via `winget install Gyan.FFmpeg` (user approved); `generate_clips.sh` produced five 10 s clips (HEVC Main10 3840x2160; HDR10 PQ/BT.2020, HLG, 23.976 fps pan, AAC 48 kHz loop clip), verified with ffprobe; 68 MB pushed to the TV's app files dir (free space 954 -> 886 MB). `push_clips.sh` spare margin is 300 MB (the TV had only ~930 MB free) and it handles Windows paths via `cygpath -m`.
- X90K startup log: HEVC hw decoder `OMX.MTK.VIDEO.DECODER.HEVC` Main/Main10/Main10HDR10/Main10HDR10Plus up to 4096x2304; hw AC-3/E-AC-3; no Dolby Vision decoder.
- Review loop 1 patches: tolerant frame-rate read, `Locale.ROOT`, `hdr=unknown` before the format is known, async-after-dispose guards, Media3 errors surfaced immediately, `SpikePlayer`/parser/lister tests, runbook corrections.
- Still open (Kay, on the TV): play each clip in texture / platform-view / media3-surface, record sharpness winner, HDR badge, 24p result, gap-free loop strategy as memlog notes.
